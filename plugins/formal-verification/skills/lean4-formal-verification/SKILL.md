# Lean 4 Formal Verification

## 目的

確率的にコードを生成する AI と、決定論的に正しさを検査する Lean 4 カーネルの役割を分離し、人間のレビュー対象を「仕様（定理文と不変条件）」へ集約する。
この skill は判断のための既定値であり、固定手順ではない。

## 適用の判断と手法の境界

- **使う場面**:
  - リポジトリにすでに Lean 4（`lakefile.lean` / `lakefile.toml` / `specs/` 等）が存在する。
  - 壊れたときの損失が大きい最小核（金額保存則、課金・サブスク状態遷移、PII/アクセス制御ポリシー、パイプライン冪等性、ID 名寄せ整合性など）に対し、形式検証や数学的保証が明示的に求められている。
- **使わない場面**:
  - 通常の CRUD、UI 変更、設定ファイルやドキュメントの修正、typo 修正、型・lint・単体テスト・通常のプロパティベーステスト（PBT）で十分に防げる変更。
  - Lean 4 が未導入のリポジトリで、依頼なしに `lean-toolchain` や `specs/` を新設しない。
- **モデル検査（TLA+ 等）との境界**:
  - Lean 4 は純粋関数的な計算ロジック、代数的不変条件、状態遷移の安全性（safety）、実行可能バイナリを使ったオラクル差分テストに適する。
  - 分散合意、非同期メッセージのインターリーブ、リトライやタイムアウトを含む並行プロトコルの活性（liveness）・デッドロック検証には TLA+ 等のモデル検査の方が適することが多い。そうした対象に無理に Lean 4 を当てはめず、手法の選定を先に確認する。
- **優先順位と重複回避**:
  - 明示的なタスク指示と対象リポジトリの `AGENTS.md` を優先する。
  - 制約を独断で緩めない原則や証拠に基づく検証の一般則は `git-development-rules` と `evidence-driven-engineering` に従い、ここでは繰り返さない。

## 3 段階の導入モデル

コードベース全体を形式化しようとせず、問題に見合う最小の段階を選ぶ。

| 段階 | 概要 | 主な用途・始めやすさ |
| :-- | :-- | :-- |
| **Level 1: 仕様・不変条件の検証** | 実装コードと独立して `specs/` に状態遷移・ポリシー・メタデータ検査を書き、`lake build` を CI ゲートにする | 導入コスト最小。権限・PII リネージ検証（DM）や状態設計の第一歩に最適 |
| **Level 2: オラクル差分テスト** | Level 1 で証明した Lean 4 仕様をバイナリ化し、同一のランダム入力・境界値に対する出力を実実装（Python / TS / SQL 等）と CI で突合する | 実務で最も投資対効果が高い。「仕様は正しいが実装がバグる」ギャップを潰す（AE / DE 等） |
| **Level 3: 実装コードの直接検証** | Rust 等の実装を Aeneas 等で Lean 4 へ持ち上げて証明する | 暗号・パーサー等の極限クリティカルパス限定。明示合意なしに選ばない |

## 人間とエージェントの責務境界

- **人間が確定・レビューする領域**: 切り出す最小核の範囲、定理文（型シグネチャと不変条件）、モデル化で割り切った前提（浮動小数点→整数スケーリング、`NULL` 扱い等）。
- **エージェントが担う領域**: モデルと定理文の提案、補題分解とタクティク探索による証明完成（`lake build` 反復）、オラクル差分テスト基盤と CI の構築。
- **仕様優先の原則**: 証明タクティクを大量に書く前、または仕様を変えるときは、人間が読める形で定理文・前提・対象外を先に提示して合意する。

## 証明の健全性（ごまかしの禁止）

- **未証明・回避手段の禁止**: 完了時点で `sorry`、`admit`、未承認のカスタム `axiom`、仕様モデル内の `unsafe` / `@[implemented_by]` / `@[extern]`、無断の `native_decide` を残さない。
- **仕様変更の禁止**: `lake build` を通すために定理の結論を弱めたり前提条件を勝手に強めたりしない。証明が通らない場合は、原因・反例候補・対応選択肢とトレードオフを示して判断を仰ぐ。
- **空虚な真（vacuous truth）の防止**: 仮定が矛盾してどんな結論も通ってしまう状態を防ぐため、仮定を満たす具体的な witness（`example` または `#eval`）を最低 1 つ用意して確かめる。
- **CI ゲートの設計**: 素朴な `grep sorry` だけに頼るとコメント誤検出や `admit`・カスタム `axiom` の見逃しが起きる。`lake build` の警告エラー化と `#print axioms` 監査を組み合わせて機械的に閉じる。

## 検証と完了報告

- リポジトリにある実際のコマンドで `lake build`、公理監査、設定された差分テストを実行し、通過を確かめてから完了とする。
- 完了時はタクティクの細部ではなく、**証明した定理一覧（自然言語の仕様訳つき）**、**依存公理の監査結果**、**実装との突合方法（Level 1 / Level 2）**、**モデル化の前提と対象外**を報告する。
