# データ領域（DE / DM / AE）での活用パターン

SQL や分散パイプラインのコード全体を Lean 4 で書き直す必要はない。一度壊れるとデータ汚染・二重計上・情報漏洩に直結し、後から修復するコストが高い最小核だけを切り出す。

| 領域 | Lean 4 で証明する不変条件 | CI への組み込み方 | 推奨段階 |
| :-- | :-- | :-- | :-- |
| **データエンジニアリング (DE)** | インクリメンタル処理の冪等性、バックフィル時の確定済みパーティション非破壊性、ID 名寄せの同値関係・順序不変性 | 状態遷移やマージ仕様を証明し、Python / PySpark 実装と出力比較 | Level 1 → Level 2 |
| **データマネジメント (DM)** | PII マスキング・アクセス制御の完全性（権限外ロールや Authorized View への非漏洩） | Terraform plan や dbt `manifest.json` を Lean 入力データへ変換して `lake build` | **Level 1**（最も導入しやすい入口） |
| **アナリティクスエンジニアリング (AE)** | 金額按分・アトリビューションの保存則（端数調整後の合計一致・非負）、サブスク MRR 状態遷移の排他性・網羅性 | Lean オラクルバイナリと dbt SQL（DuckDB 等）の出力をランダム境界ケースで突合 | **Level 2** |

---

## 1. データマネジメント (DM) — 最も低ハードルな入口

実データではなく「メタデータとポリシー」を扱うため、既存パイプラインの実行環境や SQL と突き合わせずに Level 1 だけで即座に効果が出る。

- **検証対象**:
  - `pii_high` 等の機密タグが付いたカラムが、`analyst` ロール等の参照可能な Authorized View に露出していない（必ず除外または承認済みハッシュ変換を通過している）こと。
  - テーブルや View が多段のリネージを組んでも、どの経路を辿ってもポリシー違反が起きないこと。
- **CI での組み込み**:
  1. PR 時に dbt の `manifest.json` や Terraform plan JSON から、テーブル・カラム・タグ・View 参照辺・権限ロールを抽出する小さな変換スクリプトを実行し、Lean 4 のデータ定義ファイル（または JSON 入力チェック）を生成する。
  2. `lake build`（および検査定理）を実行し、PII 素通り経路が 1 本でもあれば PR をブロックする。

## 2. アナリティクスエンジニアリング (AE) — 境界値バグの根絶

`unique`・`not_null`・`accepted_values` といった従来の dbt テストでは拾えない「計算式や状態分類の整合性」を閉じる。

### 最小例: 金額按分・アトリビューションの保存則

```lean
-- 按分関数の仕様（端数調整まで含めて定義する）
def allocate (total : Nat) (weights : List Nat) : List Nat :=
  ...

-- 定理：重みの合計が 1 以上なら、按分結果の合計は必ず元の total と一致する
theorem allocate_preserves_total (total : Nat) (weights : List Nat)
    (h : weights.sum > 0) :
    (allocate total weights).sum = total := by
  ...

-- 空虚な真でないことを示す具体例
example : ([10, 20, 70] : List Nat).sum > 0 := by decide
```

- **人間のレビュー箇所**: `allocate_preserves_total` の型シグネチャ（特に `weights.sum > 0` という前提条件と `sum = total` の結論が業務要件と合っているか）だけに集中できる。
- **CI での組み込み**:
  - `lake build` と公理監査で証明を検証したあと、実行可能オラクル `allocate` と dbt SQL（DuckDB やテスト用 BigQuery）にランダムケースと境界ケース（重み 0 を含む配列、0 円決済、1 円の 3 等分など）を流して出力を突き合わせる。

### もう一つの典型例: サブスクリプション MRR の状態遷移

- 月跨ぎで契約状態を `New` / `Expansion` / `Contraction` / `Churn` / `NoChange` に分類するとき、任意の前後契約状態ペアに対して「必ずちょうど 1 つの状態に分類され、漏れも二重計上もないこと」を定理として証明する。

## 3. データエンジニアリング (DE) — 冪等性と名寄せ

- **インクリメンタル処理の冪等性**: 同じ日付パーティション・同じ入力バッチに対してマージ処理 `step` を 2 回適用しても `step (step state batch) batch = step state batch` になること、および再計算ウィンドウ外の確定済みパーティションが不変であることを状態遷移モデルで証明する。
- **ID 名寄せの整合性**: セッションやデバイス間のリンク集合から代表 ID を引く関数が、同値関係（反射・対称・推移）と入力レコードの処理順序不変性を満たすことを証明し、PySpark / Python のバッチ実装と差分テストする。

## データ領域特有の落とし穴

- **NULL と空集合**: SQL の `SUM` は空集合で `NULL` になることがある。Lean 側では `0` になるか `Option` になるかをはっきりさせ、実装の `COALESCE` 有無と揃える。
- **リネージの循環や動的 SQL**: `manifest.json` にない動的 SQL や外部ビューは検査範囲外になるため、検査対象と対象外の境界を明確にして報告する。
- **小数・通貨丸め**: 浮動小数点（`FLOAT64`）ではなく整数（円、セント、bps）や有理数・固定小数点に正規化してから比較する。
