# データ領域（DE / DM / AE）での活用パターン

SQL や分散パイプラインのコード全体を Lean 4 で書き直す必要はない。一度壊れるとデータ汚染・二重計上・情報漏洩に直結し、後から修復するコストが高い最小核だけを切り出す。

| 領域 | Lean 4 で証明する不変条件 | CI への組み込み方 | 推奨段階 |
| :-- | :-- | :-- | :-- |
| **データエンジニアリング (DE)** | インクリメンタル処理の冪等性、バックフィル時の確定済みパーティション非破壊性、ID 名寄せの結合結果・順序不変性・冪等性 | 状態遷移やマージ仕様を証明し、Python / PySpark 実装と出力比較 | Level 1 → Level 2 |
| **データマネジメント (DM)** | 抽出したメタデータスナップショット上の PII マスキング・アクセス制御の完全性（許可外ロール・View への素通り経路がないこと） | 一般のスナップショットに対する検査関数 `check` の健全性定理（`check m = true → NoLeak m`）を一度証明し、CI で `lake exe` に抽出 JSON を渡す | **Level 1**（最も導入しやすい入口） |
| **アナリティクスエンジニアリング (AE)** | 金額按分・アトリビューションの保存則（端数調整後の合計一致・非負）、サブスク MRR 状態分類の排他性・網羅性・増減保存則 | Lean オラクルバイナリと dbt SQL（DuckDB や本番互換環境）の出力をランダム境界ケースで突合 | **Level 2** |

---

## 1. データマネジメント (DM) — 最も低ハードルな入口

実データではなく「抽出したメタデータとポリシーのスナップショット」を検査対象にするため、本番データや SQL 実行環境を使わずに Level 1 として始めやすい。

- **検証対象**:
  - `pii_high` 等の機密タグが付いたカラムが、`analyst` ロール等の参照可能な Authorized View へ「除外または承認済みハッシュ変換を通さずに到達する経路」がスナップショット上に存在しないこと。
- **CI での組み込み（検証済みチェッカー方式を既定とする）**:
  - 大規模な dbt `manifest.json` や Terraform plan を毎回 Lean ソースコードへ埋め込んで `decide` で証明しようとすると、再帰上限やタイムアウトに詰まり `native_decide` に逃げやすくなる。
  - 代わりに、**任意のグラフ `m` に対する検査関数 `check : Snapshot → Bool` と、その健全性定理 `theorem check_sound (m : Snapshot) : check m = true → NoLeak m` を一度だけ Lean 4 で証明**しておく。
  - CI では、(1) `lake build --wfail` ＋公理監査で `check_sound` を検証し、(2) 抽出スクリプトが `manifest.json` / Terraform plan 等から変換したスナップショット JSON をコンパイル済みバイナリ（`lake exe check-pii`）に流して判定する。
- **信頼境界と対象外の明示**:
  - 抽出スクリプトは信頼境界の内側にある。`manifest.json` や Terraform plan 単体では、列単位の SQL 変換・継承される有効権限・管理外ビュー・手動設定まで完全には復元できない場合がある。
  - 必要な列リネージ・変換・権限情報を取得できない場合や入力が欠落している場合は「安全」とせず**判定不能として fail-closed に落とす**。動的 SQL や管理外ビューが対象外であることも完了報告へ明記する。

## 2. アナリティクスエンジニアリング (AE) — 境界値バグの根絶

`unique`・`not_null`・`accepted_values` といった従来の dbt テストでは拾えない「計算式や状態分類の整合性」を閉じる。本番エンジン（BigQuery 等）と DuckDB の方言差が不変条件に関わる場合は、主要境界値を本番互換環境でも検証する。

### 最小例: 金額按分・アトリビューションの保存則

```lean
-- 按分関数の仕様（計算可能にして端数調整まで含めて定義する）
def allocate (total : Nat) (weights : List Nat) : List Nat :=
  ...

-- 定理：重みの合計が 1 以上なら、按分結果の合計は必ず元の total と一致する
theorem allocate_preserves_total (total : Nat) (weights : List Nat)
    (h : weights.sum > 0) :
    (allocate total weights).sum = total := by
  ...

-- 空虚な真でないことを示す具体例（全前提の充足と対象関数の具体結果）
example : ([10, 20, 70] : List Nat).sum > 0 := by decide
example : allocate 100 [10, 20, 70] = [10, 20, 70] := by decide
```

- **人間のレビュー箇所**: `allocate` の仕様定義と `allocate_preserves_total` の型シグネチャ（`weights.sum > 0` という前提と `sum = total` の結論が業務要件と合っているか）に集中できる。
- **CI での組み込み**:
  - `lake build --wfail` と公理監査で証明を検証したあと、実行可能オラクル `allocate` と dbt SQL に定義域内ランダムケース・境界ケース（重み 0 を含む配列、0 円決済、1 円の 3 等分など）を流して出力を突き合わせる（`weights = []` 等の定義域外入力は実装側のエラー／フォールバックテストで別途検証する）。

### もう一つの典型例: サブスクリプション MRR の状態分類

単一の enum 返却関数について「ちょうど 1 つの値を返す」ことを証明しても定義上自明になる。代わりに、対象とする状態ペア（例: 前期末契約額・当期末契約額・休眠状態、月次スナップショット粒度で期間内の増減を相殺した純増減、休眠→休眠や再契約の扱いを含む業務定義）に対して、**SQL の各 `CASE` / `WHERE` 条件に対応する独立した述語 `isNew` / `isExpansion` / `isContraction` / `isChurn` / `isRetained` / `isDormant` を定義**し、次を証明する。

- **排他性と網羅性**: どの有効な前後契約状態ペアに対しても、上記述語のうちちょうど 1 つだけが真になる。
- **MRR 増減の保存則**: 各区分で計算した増減額の合計が `当期末 MRR - 前期末 MRR` と一致する。

## 3. データエンジニアリング (DE) — 冪等性と名寄せ

- **インクリメンタル処理の冪等性**: 同じ日付パーティション・同じ入力バッチに対してマージ処理 `step` を 2 回適用しても `step (step state batch) batch = step state batch` になること、および再計算ウィンドウ外の確定済みパーティションが不変であることを状態遷移モデルで証明する。
- **ID 名寄せ（Identity Resolution）の整合性**: 「`rep a = rep b` が同値関係である」だけでは任意の関数で自明に成り立つため、実装が本当に満たすべき次の 4 性質を定理にする。
  1. リンクされた 2 つの ID は同じ代表 ID を持つ（健全性）。
  2. どのリンク経路でも連結していない ID 同士は異なる代表 ID を持つ（過剰統合の防止）。
  3. 入力リンク列の順序を入れ替えても各 ID の代表同値類が変わらない（入力順序不変性）。
  4. 代表解決関数が冪等である（`rep (rep x) = rep x`）。

## データ領域特有の落とし穴

- **NULL と空集合**: SQL の `SUM` は空集合で `NULL` になることがある。Lean 側では `0` になるか `Option` になるかをはっきりさせ、実装の `COALESCE` 有無と揃える。
- **リネージの循環や動的 SQL・不完全メタデータ**: `manifest.json` にない動的 SQL や管理外ビュー、変換スクリプトの抽出漏れは検証の外に出るため、欠落時は fail-closed とし、検査対象と対象外の境界を明確にして報告する。
- **小数・通貨丸め**: 浮動小数点（`FLOAT64`）ではなく整数（円、セント、bps）や固定小数点または有理数に正規化してから比較する。
