# Level 2: 実行可能オラクルによる差分テスト

Level 1 で「Lean 4 上の仕様（モデル）が数学的に正しい」ことを証明しても、Python / TypeScript / SQL などの実実装と挙動がズレていればバグは防げない。Level 2 では、証明済みの Lean 4 仕様を実行可能バイナリ（オラクル）としてコンパイルし、同一入力に対する実実装との出力一致を CI で検査する。

## 基本アーキテクチャ

1. **純粋な仕様・証明モジュール（例: `Specs/Core.lean`）**
   - `IO` を一切含めず、計算ロジックと不変条件（`theorem`）だけを記述する。
   - 公理監査（`#print axioms`）と `warningAsError` の対象にする。
2. **薄いオラクル CLI ラッパー（例: `Specs/OracleMain.lean`）**
   - `lakefile` に `lean_exe` ターゲットを定義し、標準入力（JSON Lines など）を 1 行ずつ読んで純粋関数を呼び、結果を標準出力に返す。
   - テストや集計の都合でシリアライズ／デシリアライズだけを担当し、ビジネスロジックは置かない。
3. **実装側のテストランナー（PBT / 境界値テスト）**
   - Python（`Hypothesis`）、TypeScript（`fast-check`）、あるいは SQL テスト環境（DuckDB 等）からランダム入力と既知のエッジケースを生成し、Lean オラクルと実実装の両方に同じ入力を流して一致を検証する。

## 差分テストの設計指針

- **境界値シードを必ず固定テストに含める**: ランダム生成だけに頼らず、過去の障害事例や典型的な境界値（0、空リスト、1 円単位の端数、負数・返金、同日複数イベント、境界日時）を明示的な回帰ケースとして並走させる。
- **シリアライズ層を単純に保つ**: Lean 側での複雑な JSON パーサー自作を避け、必要最小限の固定スキーマまたは単純なタブ／CSV／整数配列形式でやり取りしてもよい。テスト用の入出力変換自体にバグを混ぜないことが重要。
- **不一致が見つかったときの切り分け**:
  1. Lean オラクルが返す値が意図したビジネス要件と合っているかを確認する（仕様自体の抜けなら、人間と相談して定理とモデルを見直す）。
  2. 仕様が正しく実装がズレているなら、実実装側を修正し、その失敗入力を回帰テストへ固定する。

## 仕様と実装がズレやすい典型的な罠

| 領域 | ズレの原因 | 設計時の決め方 |
| :-- | :-- | :-- |
| **金額・割合** | 実装が `float` / `DOUBLE` を使い丸め誤差が出る | Lean 側も実装側も整数（最小通貨単位・セント・円）や固定小数点の有理数で設計する |
| **端数処理** | 切り捨て・四捨五入・銀行丸め・最大剰余法の違い | 端数調整の決定論的ルール（例: 余りを先頭または最大誤差項目へ配分）まで仕様関数に含める |
| **NULL / 欠損値** | SQL の 3 値論理（`NULL` 伝播）と Lean の `Option` の違い | `Option` で明示的に表現し、`none` 時のフォールバックを仕様に含める |
| **コレクション順序** | SQL の `GROUP BY` / `ORDER BY` 欠落や同点タイブレーク | 同値な入力順で結果が同じであることを定理にするか、決定的なタイブレークキーを明記する |
| **日時・タイムゾーン** | UTC とローカル日付（JST 等）の境界日跨ぎ | 時刻計算をエポック秒または正規化済み日付キーに落としてからモデル化する |
