# Level 2: 実行可能オラクルによる差分テスト

Level 1 で「Lean 4 上の仕様（モデル）が数学的に正しい」ことを証明しても、Python / TypeScript / SQL などの実実装と挙動がズレていればバグは防げない。Level 2 では、証明済みの Lean 4 仕様を実行可能バイナリ（オラクル）としてコンパイルし、同一入力に対する実実装との出力一致を CI で検査する。

## 基本アーキテクチャ

1. **純粋かつ計算可能な仕様・証明モジュール（例: `Specs/Core.lean`）**
   - `IO` を一切含めず、計算ロジックと不変条件（`theorem`）だけを記述する。
   - **オラクルとして実行する関数 `def` は必ず計算可能（非 `noncomputable`）にする**。証明自体が `Classical.choice` 等を使っていても、実行対象となる定義が計算可能でなければネイティブ実行できない。
   - 計算核およびその依存モジュールに `@[implemented_by]` / `@[extern]` / `unsafe` が入ると、証明した論理定義と実行バイナリの挙動が乖離するため混入させない。
   - 警告エラー化（`--wfail` / `weakLeanArgs`）と許可リスト公理監査の対象にする。
2. **薄いオラクル CLI ラッパー（例: `Specs/OracleMain.lean`）**
   - `lakefile` に `lean_exe` ターゲットを定義し、標準入力（JSON Lines など）を 1 行ずつ読んで計算可能な純粋定義だけを呼び、結果を標準出力に返す。
   - シリアライズ／デシリアライズだけを担当し、ビジネスロジックは置かない。
3. **実装側のテストランナー（PBT / 境界値テスト）**
   - Python（`Hypothesis`）、TypeScript（`fast-check`）、あるいは SQL テスト環境から入力を生成し、Lean オラクルと実実装の両方に同じ入力を流して一致を検証する。

## 差分テストの設計指針

- **定義域内テストと定義域外テストを明確に分ける**:
  - **定義域内（In-domain）**: 定理の前提条件（例: `weights.sum > 0`、`total >= 0`）を満たすランダム生成入力と境界値で、オラクルと実実装の一致および不変条件の成立を検査する。
  - **定義域外（Out-of-domain）**: 前提が落ちる入力（空配列、総和 0、負数・返金、想定外 NULL 等）について、実装が仕様どおりのエラー／拒否／フォールバックを返すかを別途テストする。
- **再現可能なシード管理と境界値シード**:
  - PBT 実行時は使用した乱数シード（または失敗入力の縮小例）を CI ログに出力・保存し、ローカルで同じ失敗を即座に再実行できるようにする。
  - ランダム生成に加え、過去の障害事例や典型的な境界値（0、空リスト、1 円単位の端数、負数・返金、同日複数イベント、境界日時）を固定の回帰テストとして並走させる。
- **比較先エンジンの実行環境に注意する**:
  - 本番が BigQuery / Snowflake などの場合、ローカルの DuckDB 等で SQL が一致しても方言固有の丸め・整数除算・NULL 処理・型変換までは保証されない。不変条件に関わる境界値は本番互換エンジンでも検証する。
- **シリアライズ層を単純に保つ**: Lean 側での複雑な JSON パーサー自作を避け、必要最小限の固定スキーマまたは単純なタブ／CSV／整数配列形式でやり取りしてもよい。テスト用の入出力変換自体にバグを混ぜないことが重要。
- **不一致が見つかったときの切り分け**:
  1. Lean オラクルが返す値が意図したビジネス要件と合っているかを確認する（仕様自体の抜けなら、人間と相談して定理とモデルを見直す）。
  2. 仕様が正しく実装がズレているなら、実実装側を修正し、その失敗入力を回帰テストへ固定する。

## 仕様と実装がズレやすい典型的な罠

| 領域 | ズレの原因 | 設計時の決め方 |
| :-- | :-- | :-- |
| **金額・割合** | 実装が `float` / `DOUBLE` を使い丸め誤差が出る | Lean 側も実装側も整数（最小通貨単位・セント・円）や固定小数点または有理数で設計する |
| **端数処理** | 切り捨て・四捨五入・銀行丸め・最大剰余法の違い | 端数調整の決定論的ルール（例: 余りを先頭または最大誤差項目へ配分）まで仕様関数に含める |
| **整数除算と剰余** | Lean の `Int` の `/` `%` と Python `//`（床方向）や SQL / JS（ゼロ方向切り捨て）は負数で結果が異なる | 負数を含みうる商・剰余は除算定義を明示し、負数の境界ケースを必ず比較する |
| **`Nat` の減算打ち切り** | Lean の `Nat` では `a - b` が `a < b` のとき `0` に丸められる | 返金・取り消し・負残高の可能性がある値は最初から `Int` でモデル化する |
| **桁あふれ（オーバーフロー）** | Lean の `Nat` / `Int` は任意精度だが、実装側は `int64` や JS の `2^53` などの上限を持つ | 扱う最大値の上限を仕様の前提（例: `total <= maxAmount`）と境界テストに含める |
| **NULL / 欠損値** | SQL の 3 値論理（`NULL` 伝播）と Lean の `Option` の違い | `Option` で明示的に表現し、`none` 時のフォールバックを仕様に含める |
| **コレクション順序** | SQL の `GROUP BY` / `ORDER BY` 欠落や同点タイブレーク | 同値な入力順で結果が同じであることを定理にするか、決定的なタイブレークキーを明記する |
| **日時・タイムゾーン** | UTC とローカル日付（JST 等）の境界日跨ぎ | 時刻計算をエポック秒または正規化済み日付キーに落としてからモデル化する |
