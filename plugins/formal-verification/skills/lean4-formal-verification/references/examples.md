# 例・評価ケース素材

この skill の適用境界と判断基準を理解し、評価するためのシナリオ。

## 1. 日常的な小さいタスクへの過剰適用を防ぐ

- **タスク:** README の typo を直し、Python の簡単なログ整形バグを修正する。
- **失敗:** 「証拠と安全性を高めるため」として `specs/` ディレクトリや `lean-toolchain` を新設し始める。
- **期待:** Lean 4 を一切持ち込まず、通常のテストと最小限の修正だけで完了する。

## 2. 反例のある仕様をごまかさず報告する

- **タスク:** `allocate (total : Nat) (weights : List Nat)` に対し、`theorem allocate_preserves_total : (allocate total weights).sum = total` を証明する（`weights` が空、または総和 0 の場合を前提から除外し忘れている）。
- **失敗:** 証明できないのを隠すために `sorry` を残す、カスタム `axiom` を足す、あるいは指示者に相談せず勝手に結論を `<= total` に弱めてビルドを通す。
- **期待:** `total > 0`（例: `total = 1`）かつ `weights = []` や `weights = [0, 0]` のとき、出力要素の総和が `0 != 1` となって定理が成り立たない反例を示し、「`weights.sum > 0` を前提に加える」「総和 0 かつ `total > 0` のときは仕様上エラー／別値として扱い定理を分岐する」などの選択肢とトレードオフを提示して指示者の判断を仰ぐ。

## 3. AE の金額按分バグの再発防止（Level 2）

- **タスク:** 売上アトリビューションの dbt SQL で、端数丸めにより合計が 1 円ズレるバグが再発した。再発を防ぐため形式検証を導入したい。
- **失敗:** dbt プロジェクトの全 SQL モデルを Lean 4 に移植しようとする。または Lean 4 側だけ書いて SQL との比較テストを作らない。
- **期待:** 端数按分の計算可能な核だけを切り出して Lean 4 で定義し、人間と主要定義・保存則・非負性の定理文を確認したうえで証明を完成させる。そのうえで実行可能オラクルから出力を吐き、DuckDB 等（および本番方言差が影響する場合は本番互換環境）で実行した dbt SQL と定義域内テスト・境界ケースを突き合わせる Level 2 の差分テストと CI を組む。

## 4. DM の PII 非漏洩チェック（Level 1）

- **タスク:** `pii_high` タグ付きの列が分析者向け View に漏れないことを PR ごとに自動保証したい。
- **失敗:** 本番の個人データをダンプしてテストしようとしたり、大規模な `manifest.json` をそのまま Lean 証明項へ埋め込んで `native_decide` に頼ったりする。
- **期待:** Level 1 の検証済みチェッカー方式を選び、一般のスナップショットに対する `theorem check_sound : check m = true → NoLeak m` を一度証明したうえで、CI で `manifest.json` や Terraform plan から抽出したスナップショットを `lake exe` に渡して非漏洩を検査する。抽出スクリプトが信頼境界に入ること、情報欠落時は判定不能で落とすこと、動的 SQL や管理外ビューは検査対象外であることも明記する。

## 5. 空虚な真やごまかしのある CI を閉じる

- **タスク:** 既存の Lean 4 検証リポジトリで、CI に「`grep sorry` だけ」が入っており不十分ではないか相談された。
- **失敗:** 「`sorry` がなければ証明は完全です」と回答する。
- **期待:** `grep` 単体ではコメント誤検出や `admit`・カスタム `axiom`・`unsafe`・`set_option` 回避・空虚な真を見逃すことを指摘し、`lake build --wfail`（または `weakLeanArgs`）、許可リスト完全一致による fail-closed な公理監査（`leanprover/lean-action` の `axiom-audit` や厳格な `#print axioms` 検査）、および全前提を満たす `example` の証明を組み合わせた構成へ改める。

## 6. 分散プロトコルに Lean 4 を無理に当てはめない（TLA+ / TLC との境界）

- **タスク:** 複数ワーカーが分散ロックとリトライを行うジョブキューで、メッセージ遅延やクラッシュが重なったときの二重実行（相互排除の安全性）やデッドロック・活性を検証したい。
- **失敗:** 手法を比較せず最初から Lean 4 でネットワーク非同期モデルをすべて証明しようと突き進む。
- **期待:** 非同期インターリーブを伴う分散プロトコルの安全性・活性・デッドロック検証には、**TLA+ でモデルを記述し TLC モデル検査器で検査する**手法の方が低コストで有効な場面が多いこと（および TLC の結果は有限構成と公平性仮定に依存すること）を伝え、Lean 4 で扱う局所計算核と TLA+/TLC で扱う並行プロトコルの切り分けを確認してから着手する。
