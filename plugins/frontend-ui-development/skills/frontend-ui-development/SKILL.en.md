# Frontend UI Development

## Purpose

Do not let the UI become a collection of ad-hoc patches.
The default design convention is [Astryx](https://github.com/meta/astryx): compose screens from Astryx templates, components, and design tokens instead of inventing components, spacing, or colors per screen.
This skill provides defaults for judgment, not a fixed procedure.

## Handling instructions

- Explicit task instructions, applicable `AGENTS.md` files, and hard constraints in the repository take precedence.
- If the project has an `<!-- ASTRYX:START -->` block generated by `astryx init`, it matches the installed version and takes precedence over this skill.
- Do not use this skill as a reason for unnecessary approval waits, excessive investigation, or scope expansion.

## Whether to use Astryx

| Project state | Approach |
| :-- | :-- |
| Uses `@astryxdesign/core` | Follow the Astryx conventions. |
| New React 19+ UI, or React 19+ without a design system | Build with Astryx. See "Adoption" in `references/astryx.md`. |
| Another design system or component library is established | Do not mix Astryx in piecemeal; mixing is what creates patchwork. Follow the existing conventions and migrate whole screens only when the user asks. |
| Not React (Vue, Svelte, etc.), or React 18 and earlier | Astryx does not apply (it requires React 19+). Use existing components and tokens and apply only the general principles from "Fix the structure" onward. |

The next two sections, "Astryx sources" and "Astryx conventions", apply only when you decided to build with Astryx. Otherwise, do not use the Astryx MCP or CLI; prefer the existing design system's components and tokens in the same spirit.

## Astryx sources

Do not write component props or import paths from memory or guesswork. Check in this order:

1. **Astryx MCP** (this plugin connects it as the `astryx` server): `search("<what you need>")` to find candidates, then `get("<Name>")` for props, examples, and the install command.
2. **Project CLI**: it answers for the installed version, so prefer it when it disagrees with the MCP. Use `astryx build "<idea>"`, `astryx template`, `astryx component <Name>`, and `astryx docs <topic>`.
3. If neither is available, say so and do not fill in unverified props by guessing.

## Astryx conventions

See `references/astryx.md` for details and CLI steps. The core rules:

- **Start pages from a template**: scaffold the template `astryx build` names, keep its frame, gap, and padding, and replace the content. When changing an existing page, do not rebuild it from a template; add blocks or components inside its sections.
- **Use components for everything they cover**: do not build layout or visuals from raw `<div>` / `<span>`. Leave layout and spacing to Stack-style components.
- **Use tokens for values**: no raw hex/px for color, spacing, radius, or shadow. Do not change the look with `style={{…}}`, imported ad-hoc CSS, or `:root` overrides. Change colors and palettes through the theme.
- **Styling order**: component props first, then the styling system the project has configured (`xstyle` with StyleX, token-backed utilities with Tailwind, otherwise `var(--color-*|--spacing-*|--radius-*)`).
- **Dense data as rows**: render lists with Table or List/Item instead of wrapping each row in a Card. Badge is for counts and enumerated states.
- **Do not invent props**: read `get` / `astryx component` before use. Forms are controlled (`value` + `onChange`); navigation uses `useLinkComponent()`.
- **Final self-check**: re-read the files you wrote and replace raw elements, `style={{…}}`, ad-hoc CSS, and hardcoded hex/px with components or tokens.

## Fix the structure

For alignment or visual bugs, do not immediately add `margin-*`, `top/left`, transforms, or selector overrides. Check the template frame, the parent Stack/gap, and component props first. Read `astryx docs layout` before changing a template's frame.

When you build what Astryx lacks, keep this dependency direction:

```text
Astryx tokens / theme
    ↓
Astryx components (swizzle to own one when needed)
    ↓
Domain / Feature Components
    ↓
Pages / Screens (start from an Astryx template)
```

If an Astryx component has the same role, do not build a similar generic one. Avoid `!important`, deep selector chains, and unexplained z-index increases.

## Development phases

Infer the phase from the request and existing code only when it matters. Phases do not relax the Astryx conventions; they change how far to polish.

- **EXPLORE**: iterate quickly on information architecture and flow by swapping templates and components. For new GUIs or large redesigns, see `references/visual-design.md`.
- **STABILIZE**: clean up provisional implementation of the UI being adopted. See `references/stabilization.md`.
- **PRODUCTION**: check accessibility, responsive behavior, states (empty/loading/error), and tests for important interactions.

## Validation

Run the smallest meaningful validation proportional to the change.

- Run checks the repository requires.
- Before delivering, run `astryx doctor --built <dir>` when the project's CLI supports it, and do not deliver while it fails.
- For visual changes, inspect the affected surfaces in a browser, Storybook, or screenshots when available.
- Once relevant checks pass, do not broaden or repeat validation without a concrete reason.

## Maintaining AGENTS.md

In an Astryx project, run `astryx init --features agents` to write version-matched rules into `AGENTS.md` (and into `CLAUDE.md` when one exists). Add `--agent all` to also write a Claude Code file reliably (`.claude/CLAUDE.md` when there is no `CLAUDE.md`).
For other project facts, use `assets/AGENTS.frontend.md` as a template and record only real paths, theme, styling system, and validation commands. Do not restate general principles.

## On completion

When useful, briefly explain the template used, newly built components, and any place left as an exception because tokens could not express it, so the rationale can be understood later.
