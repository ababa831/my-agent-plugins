# 指摘を持続する制約に変える

同じ誤りが再発しうるとき、プロンプトに注意書きを足すだけで終わらせず、誤りを許している環境を改善する。

## 手段の選び方

最小で効く手段を選ぶ。

| 失敗の性質 | 有効な対応 |
| :-- | :-- |
| 不正な状態や依存を設計でなくせる | アーキテクチャ、API、データモデルで制約する |
| 悪いパターンを機械的に検出できる | 型、lint、コンパイラ、CIのチェックを追加または再利用する |
| 判断に文脈が要る | 簡潔なプロジェクトルールやレビュー基準を書く |
| エージェントに再現可能な手順が欠けている | 手順をskillにまとめ、その振る舞いを評価する |

- 実現できるなら、強制できる制約を優先する。文章のルールや自動レビューは、あくまで誤りうる指針である。
- 新しいチェックは、悪いケースを拒否し、正しいケースを通すことを両方確かめる。
- 一般的な原則と適用条件を記録する。発端となった出来事の固有名や経緯は書かない。似た指示を増やさず、既存の指示を拡張する。
- 対象プロジェクトの制約に従う。あるプロジェクト固有の禁止事項（コメント禁止、特定APIの禁止など）を、どこでも通用する禁止事項として持ち込まない。
- タスクの範囲を超える設計変更は、範囲を区切った後続作業として残す。

## 推奨経路を健全に保つ

実装への最短経路が、意図した設計に沿うようにする。

- 正規のヘルパーやモジュールが要件を満たすなら、それを使う。機能が足りない場合は、競合する実装を足す前に、範囲を絞った改善を検討する。
- 複数のパターンが衝突しているときは、使われ方と制約を調べてから選ぶ。
- 保守作業では、古くなった例と呼び出し元をまとめて更新する。既存の負債をすぐ消せない場合は、既存の例外を記録したうえで新しい発生を防ぐことを検討する。
- 新しいプロジェクトでは、エージェントが最初の実装を各機能へ複製する前に、最小限の動く例を用意し、重要な境界を強制する。
